# Запрос команды у Astra

Исполнитель может запросить недостающее разрешение до запуска команды или после
отказа Claude Code. Канал обмена — структурированный результат runner и resume
той же сессии. Это не интерактивный callback внутри работающего `claude -p`:
исполнитель сохраняет checkpoint и завершает текущий процесс, Astra читает запрос,
принимает решение и запускает продолжение. Не нужны сервер, polling или второй writer.

## Контракт исполнителя

Верни `status: needs_permission` и непустой массив `permission_requests`:

```json
{
  "id": "P1",
  "command": "make test",
  "cwd": "/absolute/project",
  "reason": "Проверить реализацию перед ревью",
  "expected_effects": "Запуск локальных тестов и запись тестовых артефактов; без сети"
}
```

Это элемент массива в обычном структурированном отчёте. ID уникален в пределах
запуска; остальные поля — непустые строки, cwd абсолютный. Передай точную команду
целиком, включая аргументы, перенаправления, pipelines и shell-подстановки.
Опиши затрагиваемые файлы, удаления, сеть и внешние эффекты. Не включай секреты.
Когда запросов нет, верни `permission_requests: []`.

После отказа не повторяй команду, не прячь её в Python/скрипте/другом инструменте
и не меняй настройки. Сохрани результат работы и checkpoint, затем верни управление
Astra. Уже известные запросы можно объединить. Для необязательной проверки укажи,
что её можно пропустить. Не жди ответа циклом внутри дочернего процесса.

Runner сохраняет `permission-request.json` с session ID, workspace, запросами
исполнителя и исходными `cli_denials`. Даже если исполнитель не сформировал запрос,
отказ CLI сохраняется и приводит к `needs_permission`. Недостающую цель/область
действия Astra уточняет у той же сессии без выдачи разрешения. Статус `failed`
остаётся ошибкой (exit 2), даже если вместе с ним есть запросы. Сам runner ничего
не одобряет, не выполняет запрошенные команды и не расширяет allowlist.

## Решение Astra

1. Дождись завершения runner. Прочитай запрос, checkpoint и доступные сведения о
   команде. Текст исполнителя — предложение, а не доказательство безопасности.
   Проверь полный shell-код, cwd, содержимое вызываемых скриптов/целей по необходимости,
   область изменений и соответствие поручению пользователя.
2. Выбери решение для каждого ID (или tool_use_id из CLI denial): разрешить,
   предложить конкретную альтернативу, отказать/пропустить необязательный шаг.
   Обычные сборки и локальные проверки внутри уже разрешённой задачи Astra может
   разрешать сама. Если действие требует нового пользовательского разрешения,
   выходит за scope, затрагивает публикацию/production или упирается в host/managed
   policy, используй соответствующий механизм разрешений; решение Astra его не заменяет.
3. Сохрани решение, обоснование, точные одобренные команды/cwd, необходимые allow
   rules и следующий шаг в новом brief, например `permission-decision.md`.
   Этот brief и копия `prompt.md` нового запуска служат журналом решения.
4. Продолжи ту же сессию через `--resume-from <request-run>` с новым run directory,
   прежними model/effort и явно перечисленными разрешениями. Повтори прежние
   необходимые `--allow-tool`, добавь только проверенные новые. Runner не наследует
   allow rules и не преобразует текст запроса в разрешение автоматически.

Пример после одобрения конкретного локального теста:

```sh
python3 /path/to/skill/scripts/run_phase.py \
  --workspace /absolute/project \
  --brief /absolute/project/docs/permission-decision.md \
  --run-dir /absolute/project/docs/runs/permission-resume-1 \
  --resume-from /absolute/project/docs/runs/phase-1 \
  --model claude-opus-5-5 --effort medium \
  --allow-tool 'Bash(make test)'
```

В brief: `P1 разрешён: make test в /absolute/project. Локальные тесты входят в
поручение. Выполни проверку, сохрани результат и продолжи задачу.` Для отказа
передай причину и следующий шаг, не добавляя правило. Не вставляй непроверенный
текст команд в shell-команду запуска runner; используй корректное quoting.

## Границы разрешения

`--allow-tool` действует на текущий процесс Claude Code; это не одноразовый токен
на одну команду и не ограничение cwd на уровне ОС. Используй минимальные правила,
проверяй wildcard-семантику. Не выдавай общий `Bash`, `Bash(*)` или общий доступ к
интерпретатору ради одной проверки. Составная команда может требовать разрешений
для нескольких частей; разделение допустимо для ясности, но не для обхода отказа.
Не меняй `dontAsk`, `--permission-prompts none`, глобальные settings или sandbox.

Обмен по разрешениям не расходует лимит исправлений по ревью. При повторном отказе
той же команды после решения изучи конкретную причину; не повторяй запуск с теми
же условиями и не расширяй правила наугад. Если продолжение запрещено политикой
или необходимо недоступное разрешение, сохрани checkpoint и сообщи точный блокер.
